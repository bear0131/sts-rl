# 文档与代码分工

> 写文档总是会变成“哎呀好多文档都过期了，还有好多信息散落在 18 个文档里，我们写一个总文档汇总所有东西吧！”于是好了现在好多信息散落在 19 个文档里了。
>
> 文档纪律应该是什么样的？哪些信息应该靠文档，哪些信息应该靠代码？尤其是在迭代很快的早期开发中。

这事太真实了。很多团队所谓“写总文档”，本质上是在制造第 19 个信息副本。**文档纪律的核心不是“多写文档”，而是：每类信息只能有一个权威来源，其他地方只能链接它，不能复述它。**

我会把原则压成一句话：

> **文档记录“为什么”和“怎么协作”，代码表达“现在实际是什么”。**

## 一、文档应该承担什么

文档最适合保存那些**代码无法自解释、也不应该藏在代码里的东西**。

### 1. 决策与背景

比如：

- 为什么选 PostgreSQL 而不是 MongoDB
- 为什么暂时不做多租户隔离
- 为什么这个模块先写死而不是做成插件
- 某个技术债是主动接受的，还是忘了还

这些东西靠代码看不出来。代码只能告诉你“现在怎么做”，不能告诉你“为什么当初这么做”。

这里适合用 **ADR / Decision Log**，一条决策一页，不写巨型历史长文。

格式可以很短：

```text
# Decision: Use Stripe Checkout first, not custom payment flow

Status: Accepted
Date: 2026-06-24
Owner: Helen

Context:
We need paid trials quickly. Custom checkout would delay launch.

Decision:
Use Stripe Checkout for v1.

Consequences:
Less UI control, but faster implementation. Revisit if conversion suffers or enterprise customers require custom terms.
```

### 2. 人和团队协作规则

比如：

- 谁负责哪个系统
- 哪些改动必须过 review
- release 流程是什么
- incident 怎么响应
- on-call 怎么升级

这些不是代码的一部分，但团队需要共同遵守。

### 3. 产品意图和用户语境

比如：

- 这个 feature 是为哪个用户痛点做的
- 成功指标是什么
- 现在明确不做什么
- 哪些行为是产品原则，不只是实现细节

这类文档应该偏“意图”，不要写成“按钮在右上角，接口叫 `/api/foo`”这种很快过期的实现清单。

### 4. Onboarding 和系统地图

新人需要的是地图，不是百科全书。

好的 onboarding 文档应该回答：

- 这个系统大概分哪几块
- 本地怎么跑起来
- 常见坑在哪里
- 要改某类功能应该从哪里开始看
- 关键代码入口在哪里

它不应该复制代码结构，也不应该手写完整 API 列表。

## 二、代码应该承担什么

只要信息可以被代码、类型、测试、配置、schema、CI 自动表达，就尽量不要手写文档维护。

### 1. API 契约靠代码或 schema

不要手写一份“当前 API 参数说明”，然后代码里又是另一套。

更好的来源：

- OpenAPI / Swagger
- GraphQL schema
- protobuf / Avro schema
- TypeScript types
- request / response tests
- contract tests

文档里最多写：

> API contract is generated from `openapi.yaml`; do not edit API docs manually.

### 2. 业务规则尽量靠测试表达

比如：

- 免费用户每天最多生成 5 次
- 订单取消后 7 天内可恢复
- 管理员可以看到所有 workspace

这些规则如果只在 Notion 里，迟早过期。更好的方式是写成测试。

文档可以解释“为什么是 7 天”，但“现在到底是不是 7 天”应该由代码和测试证明。

### 3. 配置、环境变量、权限靠可执行来源

环境变量不要手写在 5 个文档里。

更好的来源：

- `.env.example`
- config schema
- Terraform
- Kubernetes manifest
- secret manager naming convention
- startup validation

文档只保留：

> Local setup reads required variables from `.env.example`.

### 4. 架构边界靠代码结构强化

如果文档说“billing 不能直接访问 workspace internals”，但代码没有任何约束，那文档迟早变成愿望清单。

边界应该靠：

- package/module visibility
- lint rule
- dependency rule
- interface
- test
- CI check

文档写原则，代码 enforce 原则。

## 三、最重要的纪律：不要复制事实

这是防止 19 个文档变 20 个文档的关键。

坏文档长这样：

> 当前登录系统使用 OAuth，入口在 `auth.ts`，支持 Google 和 GitHub，用户表字段有……

这种会很快坏。

好文档长这样：

> Auth source of truth:
> - OAuth providers: see `auth/providers.ts`
> - user schema: see migration files
> - login product behavior: see `Product/Auth.md`
> - decision history: see ADR-004 and ADR-009

也就是说，**汇总文档应该是索引，不是复印机。**

## 四、信息分类表

| 信息类型 | 应该放哪里 | 原因 |
|---|---|---|
| 当前字段、接口、枚举、配置 | 代码 / schema / generated docs | 变化快，必须可验证 |
| 业务规则当前行为 | 测试 + 代码 | 文档容易撒谎，测试会失败 |
| 为什么这样设计 | 文档 / ADR | 代码看不出背景 |
| 产品目标和非目标 | 产品文档 | 需要人类语境 |
| 系统如何本地启动 | README + scripts | README 给入口，script 才是真相 |
| 部署流程 | CI/CD 配置 + runbook | 能自动化就自动化 |
| 操作事故处理 | runbook | 人需要步骤和判断 |
| 权限、依赖、边界 | 代码结构 + lint/CI + 简短文档 | 只靠文档不够 |
| Roadmap | 项目管理工具 / planning doc | 本来就会变 |
| 历史方案比较 | ADR / archived RFC | 保留推理，不污染当前状态 |

## 五、早期高速迭代时的文档策略

早期最大的问题不是“没有文档”，而是**文档比产品还快腐烂**。所以早期文档要轻、短、可删除。

我会用这几类：

### 1. `README.md`：只写启动和入口

不要把 README 写成百科全书。

它只负责：

- 项目是什么
- 怎么跑
- 怎么测试
- 主要目录
- 哪里找更多信息

### 2. `docs/architecture.md`：只写稳定边界

不要每天更新架构图。早期架构文档只写：

- 系统有哪些大块
- 哪些模块不应该互相依赖
- 数据流大概怎么走
- 重要 tradeoff

保持一页以内最好。

### 3. `docs/decisions/`：小型 ADR

每个重要决定一篇。不要回头把历史洗成“我们早就想好了”。

状态要明确：

```text
Proposed / Accepted / Superseded / Deprecated
```

### 4. `docs/runbooks/`：只写真的会救命的操作步骤

比如：

- 怎么回滚
- 怎么手动补偿订单
- 怎么处理 webhook 重放
- 怎么恢复误删数据

Runbook 要偏命令和判断，不要长篇解释。

### 5. `docs/product/`：写用户意图，不写实现流水账

产品文档可以写：

- 用户是谁
- 问题是什么
- v1 做什么
- v1 不做什么
- 成功指标是什么

但不要把每个按钮状态都当圣经，除非它已经是稳定规范。

## 六、每个文档必须有“死亡机制”

没有死亡机制的文档，最后都会变成考古遗址。

每个文档顶部最好都有：

```text
Status: Active / Draft / Deprecated / Superseded
Owner: @someone
Last reviewed: 2026-06-24
Source of truth: code / this doc / generated docs / external system
Review trigger: before launch / after auth rewrite / when billing changes
```

尤其是 `Source of truth` 很重要。

如果一个文档不是权威来源，它必须明确说：

> This document is an overview. Do not update implementation details here.

## 七、团队流程上怎么执行

我觉得有效的规则是这些：

**第一，改代码时，如果改变了外部行为，同一个 PR 必须改测试或生成 schema。**

不是先改 Notion。

**第二，改“为什么”时，写 ADR。**

不要把决策塞进 Slack、PR comment、会议纪要里，然后三个月后没人找得到。

**第三，文档里不允许复制可生成信息。**

比如 API 参数、数据库字段、feature flag 默认值、环境变量列表。除非这个文档就是生成出来的。

**第四，发现旧文档不要“顺手补一个总文档”。**

正确动作是：

1. 找出权威来源
2. 删除或标废旧文档
3. 建一个索引链接到权威来源
4. 把重复内容删掉

**第五，文档 review 要问一句：这篇文档会不会制造第二个真相？**

如果会，就不要写，或者改成索引。

## 八、一个很好用的判断标准

写文档前问三句话：

### 1. 这个信息能不能由代码表达？

能，就放代码、测试、schema、配置、CI。

### 2. 这个信息会不会频繁变化？

会，就不要手写长文档。用自动生成、链接、或者短状态说明。

### 3. 这个信息是不是解释“为什么”？

是，就写文档，而且要写得短、带日期、带状态。

## 九、最推荐的文档体系

早期团队我会用这个最小集合：

```text
README.md
docs/
  architecture.md
  decisions/
    0001-use-postgres.md
    0002-use-stripe-checkout.md
  runbooks/
    rollback.md
    incident-response.md
  product/
    auth.md
    billing.md
```

再加几个代码内权威来源：

```text
openapi.yaml / generated API docs
.env.example
database migrations
tests/
config schema
CI workflows
```

这套东西的精神是：

> 文档负责导航、解释、决策和协作；代码负责事实、约束、行为和当前状态。

## 十、最危险的文档类型

要特别警惕这几种：

1. **“系统全貌大文档”**
   很爽，但很快过期。应该改成索引。

2. **“当前实现细节说明”**
   只要代码一改，它就坏。应该让代码、schema、测试表达。

3. **“会议纪要冒充决策文档”**
   会议纪要记录讨论，ADR 记录决定。两者不能混。

4. **“TODO 文档”**
   TODO 应该进 issue tracker。文档里只保留原则和背景。

5. **“复制粘贴型 onboarding”**
   新人读完还是不知道该看哪里。onboarding 应该是地图，不是百科。

---

我会把文档纪律总结成这几条：

> **一个事实，一个来源。**
> **文档写原因，代码写真相。**
> **汇总文档只做索引，不复制内容。**
> **能自动生成的，不手写。**
> **每篇文档都要有 owner、status 和过期机制。**
> **早期文档宁可短、丑、可删，也不要长、全、没人敢动。**

最好的文档不是“把所有东西写下来”，而是让团队永远知道：**我应该去哪里找真正可信的答案。**
