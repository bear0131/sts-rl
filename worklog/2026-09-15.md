# 2026-09-15

## Rollout HP ordering metric diagnosis

用户询问 `rollout_value_gt_current_hp_ge_future_hp_fraction` 曲线不稳定的原因。未修改运行代码或远端训练。

静态核对发现：

- 指标在 `rl/algorithms/accumulating_ppo.py:1037-1113` 按当前 collection 窗口计算，不是跨窗口累计统计；只纳入本窗口内完成战斗的 roots，跨窗口仍在进行的战斗延后到以后窗口，样本组成和分母会随战斗长度、终局时刻、policy 行为变化。
- 它统计的是失败事件 `estimated_value > current_hp >= future_hp` 的比例，而不是“输出低于当前 HP”的成功率；因此曲线升高代表更差，且不能直接当作 value 学习曲线。
- `estimated_value` 是 collection 时根部 `core.actor_critic` 的直接输出；W&B 记录发生在后续 inner optimizer update 之后，因此图上的训练 step 与被测参数存在一个 collection/update 时序差异。
- native combat 的 `step_native_combat()` 先保存胜利战斗状态，再调用 `_settle()`；当前监控使用 `_next_phase_hp(new_obs, ...)` 得到的 `future_hp`，即结算后的普通 observation。结算回血会造成 `future_hp > current_hp`，而当前条件对这类样本永远不匹配，却仍计入 count。
- 分布式汇总在 `rl/training/distributed_sb3.py:2356-2402` 对各 rank 的 fraction、count、matches 做标量平均；fraction 的严格全局统计应使用 `sum(matches) / sum(count)`，不能在 rank 样本数不同或 healing 比例不同的情况下保证等价。
- value head 是线性输出，没有硬性限制在 `[0,1]`；MSE 目标只能软性推动它接近最终 HP，不能保证每个状态满足 value <= current HP。replay 与每轮五次 inner update 也会使当前采样分布和训练后输出暂时不一致。

后续若修复，建议拆成：非回血战斗上的 `estimated_value <= current_hp` 成功率；`current_hp - estimated_value` 的均值/分位数；以及用战斗胜利前 terminal combat state（而非 settlement 后 HP）作为 future HP 的独立统计，并在分布式端汇总原始 count/matches 后再计算 ratio。
