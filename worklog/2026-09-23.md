## Historical wholerun effective-batch audit

User asked whether the historical `wholerun-hier-hp-a0-lr3e-4-ebs262144`
run combined samples and gradients across four machines instead of performing
four independent updates.

The downloaded W&B configuration at `C:\Users\Tony2\Downloads\config.yaml`
identifies `world_size=4`, `n_envs=128`, `n_steps=512`, `batch_size=4096`,
`gradient_accumulation_steps=16`, `n_epochs=10`, and learning rate `3e-4`.
Thus each rank collected `128*512=65,536` transitions, used 16 local
4,096-sample microbatches per epoch, and accumulated a local effective batch of
65,536. The four-rank global effective batch reported by W&B was
`4,096*16*4=262,144`; each rollout epoch performed one synchronized optimizer
step, for ten synchronized steps per rollout.

The distributed implementation validates the local rollout divisibility,
iterates `rollout_buffer.get(batch_size)` independently on every rank, divides
the local accumulated gradient by the number of local microbatches, then calls
`synchronize_gradient_step`. The SSH ring sums the flat gradients and divides
by `world_size`; every rank then runs Adam on the same averaged gradient. Raw
rollout samples are not copied to a central host. With equal local sample
counts and the same loss normalization, this is mathematically the gradient
of the union of all four local batches, so the W&B value is a global effective
batch rather than four independent effective batches.

The archived `docs/archive/docs/current-wholerun-training.md` describes a
different historical `wrcv10h` run with `128*2048` local rollout,
`8192*8` local accumulation, and the same global effective-batch value
`8192*8*4=262,144`; it follows the same four-rank aggregation semantics.
No training configuration, checkpoint, or remote process was changed during
this audit. Evidence: `C:\Users\Tony2\Downloads\config.yaml`,
`rl/training/distributed_sb3.py`, `rl/training/ring_allreduce.py`, and the
archived wholerun training record.

## Analysis: small `n_steps` and pending-label latency

User asked for an idealized mathematical explanation of why a small
`n_steps` can make training updates appear slower. No code, configuration, or
remote training state was changed for this analysis. Let `E=n_envs`,
`T=n_steps`, and hold the per-rank rollout product `B=E*T` fixed. If combat
roots arrive at rate `lambda` per environment transition and their terminal
label latency is `L` transitions, a root born near the end of a collection is
still pending at its boundary with probability `P(L>u)`. The same-block
contribution is therefore

`C_within(T)=lambda*B/T * integral_0^T P(L<=u) du`,

while the new roots not finished inside that block contribute

`P_within(T)=lambda*B/T * integral_0^T P(L>u) du`.

These expressions are not the full steady-state pending queue because this
implementation carries `_nosl_is_az_pending_fights` across collections. By
Little's law, the total in-flight root count is approximately
`Q(T)=lambda*B*E[L]/T`; hence reducing `T` by 8 while preserving `B` can
increase simultaneous pending roots, metadata, and boundary/IPC pressure by
about 8. In a stationary ideal system the mean completed roots per block can
still approach `lambda*B`; the penalty is label delay in collection rounds,
approximately `E[L]/T`, plus the larger pending queue and higher chance of
phase-synchronized empty collections during startup or resets.

The current replay gate makes this operationally important: only finite
`value_target` samples enter replay, and with `max_old_fraction < 1` a
collection with zero fresh roots returns `train_count=0`. For the active preset
(`batch=98304`, `microbatch=24576`, `U=40`, old fraction `0.90`), a nonempty
fresh partition permits a full `40*4=160` gradient-batch group, while zero
fresh roots permits zero batches. Thus pending can reduce effective updates per
wall-clock time without making a valid full backward pass intrinsically slower.
Any claim that backward itself slowed must compare rounds with identical
`batch_size_used` and `gradient_batches`, separately from collection/pending
time.

## Analysis: whether 256 CPU cores can reach 1000 env steps/s

User proposed 256 CPU cores, 128 model evaluations per search, and a 1M
parameter model. Under the idealized assumption that one forward costs only
1M MACs, 1000 env steps/s requires `128e9 MAC/s` (about `256 GFLOP/s` when a
MAC is counted as two FLOPs), or only `0.5e9 MAC/s` / `1 GFLOP/s` per physical
core. That arithmetic makes 1000 aggregate steps/s plausible.

It is not a valid estimate for the current Transformer specialist. A shared
Transformer weight matrix is applied once per token, so parameter count is not
forward FLOPs. For `d=100`, `L=8`, feed-forward width `4d`, and `S` active
combat tokens, the main encoder cost is approximately

`F_leaf ~= L * (24*S*d^2 + 4*S^2*d)` FLOPs,

before tokenization and heads. This is about 82 MFLOP at `S=40`, 127 MFLOP at
`S=60`, and 224 MFLOP at `S=100`. With 128 leaf evaluations per env step,
1000 steps/s therefore demands roughly 10--29 TFLOP/s sustained aggregate,
or 40--113 GFLOP/s per core across 256 cores. BF16/AMX and large batched
inference could approach the lower end on suitable hardware; ordinary
batch-1 PyTorch CPU inference, search traversal, environment transitions,
masking, state copies, and IPC make it unlikely.

At 1000 steps/s the system must process 128,000 leaves/s. With inference
batches of 128 that is 1000 model batches/s, so the entire CPU inference path
has roughly a 1 ms batch budget. Weight reuse across a batch is essential: a
2--4 MB model can stay in cache, whereas 128,000 independent batch-1 calls
would create hundreds of GB/s of weight traffic and incur scheduling overhead.
The current worker/Python/pipe architecture would need a colocated native
threaded search plus persistent batched CPU inference service to target this
number.

Therefore: 1000 env steps/s is a plausible stretch target for a dedicated
256-physical-core host only after a native, batched CPU pipeline is built; it
is not supported by the `128*1e6` calculation alone. A fair benchmark must
report actual leaves/s, inference batch sizes, search/tree time, env
transition time, IPC/synchronization, and end-to-end env steps/s. If the 256
CPUs are distributed over hosts, network/IPC overhead must be included and
the target is correspondingly harder.
