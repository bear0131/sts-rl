# 遗物无规则锁定模式评估

## 结论

这个方向适合普通战斗遗物。遗物集合是有限且稳定的，绝大多数遗物在战斗中不是被主动选择的规则文本，而是持续存在的机制开关。把它们和 buff 一样放进固定槽位的 0/1 存在向量，可以移除遗物规则 Transformer、规则 token 和无效的规则描述注意力，减少输入长度，并让状态变化直接落在固定向量位置上。

这不是“遗物完全没有语义”，而是把语义从规则文本泛化改成固定槽位语义：模型通过训练学习 `RELIC_SLOT_x=1` 对应的行为。因而槽位顺序一旦用于训练就必须稳定，不能按当前遗物列表的动态顺序编码。

## 建议的状态接口

```text
player.relic_presence[slot] = 0 or 1
player.relic_counter[slot]  = environment-owned value, queried only when needed
```

- `relic_presence` 使用一个固定长度向量；每个位置绑定一个稳定的普通遗物 ID，遗物不存在为 0，存在为 1。
- 遗物的计数器不放进规则向量，也不因为存在位为 1 就自动伪造一个计数器。只有确实拥有计数器的遗物允许模型发起读取请求，环境返回该槽位的精确数值。
- 计数器改变时写入对应 `relic[slot]` 的 delta；没有计数器的遗物永远不会产生计数读写事件。
- 训练数据生成器应维护“遗物是否有计数器”的元数据，并对非法计数查询做验证或查询 mask，避免模型学到燃烧之血、纸蛙等不存在计数器的假接口。

## Boss 遗物

Boss 遗物可以继续占用固定的 Boss 槽位。楼层决定哪些 Boss 槽位可选，环境在选择完成后将被选中的槽位置 1；选择过程可以作为独立的环境事件，不需要把 Boss 遗物效果规则再次编码进每个战斗样本。若需要表达“可选但尚未选择”，应另设 `boss_relic_available` 或选择事件状态，不能把“0”同时解释成“不可选”和“未拥有”。

## 与当前 v6 的关系

当前 v6 checkpoint 仍使用 `relic_encoder` 和按列表位置对齐的 `relic_counter_slots`。因此本评估是 v7 后续协议建议，不代表本次 PCA 已经修改训练模型。正式切换时需要同时更新状态布局、数据生成器、world encoder 输入和计数器查询验证，并固定一份 append-only 的遗物槽位表；否则旧 checkpoint 不能直接加载新布局。

## 主要风险

固定槽位会牺牲对未见遗物的规则组合泛化，但这对“遗物集合固定、普通遗物不需要选择”的战斗建模通常是可接受的。若以后要加入新遗物，应追加新槽位并重新训练或做兼容迁移，不能重排旧槽位。
