
### Runtime evaluation semantics and history audit

User intention: “它 runtime 是怎么 eval 的？……跑多少步之后专门跑个 100 局 eval……看看是什么时候变的，还是一直如此”。Scope: read current training metrics, distributed aggregation, explicit evaluation CLI, and Git history; no training or remote operations. Baseline main 2d4f209cf95407539c83b2562684cbd3c5cc295c; initial worktree clean.

Findings: StSMetricsCallback consumes completed training episodes from infos, keeps per-rank deque(maxlen=metrics_window), default100, and records means at rollout end. distributed_sb3 aggregates game metrics by rank mean after learning and publishes once per collection/update cycle. Current fourfold preset96env ×128steps ×4ranks gives49152 global transitions per collection;40 learner updates do not mean40 new evaluation batches. Windows may overlap and include trajectories crossing policy updates; incomplete windows are averaged by rank, not weighted by episode count. Explicit rl.evaluation.eval defaults to100 episodes but is not invoked by the trainer.

History verified via git show/log -S/-G: 583ecea (2026-06-24) introduced whole-run StSMetricsCallback with rolling100 and rollout-end logging; e988492 (2026-06-26) moved it into task architecture; f3696a9 (2026-09-10) changed game logging from rank0 to rank-mean aggregation; September13 module/backend refactors did not introduce rolling statistics. Legacy overfit_test in583ecea explicitly evaluated after the entire training call, default50 episodes, not periodically100.

Validation: static source/history inspection only (rg, git show, git log, current configs and launcher); no runtime tests necessary for documentation-only audit. No outstanding implementation work; remote process arguments were not queried.
