## 当前四机训练吞吐瓶颈复查

用户原始意图：“继续前面调查训练速度瓶颈”。本节只做远端只读 profiling，未停止、重启、调参
或修改训练代码。对象为 `u40x4-20260915` / W&B `u40x4s15` 的四机运行，配置仍为每 rank
96 env、24 worker（每 worker 4 env）、`n_steps=128`、Full-Gumbel 128 simulations、
`leaf_batch_size=1`、inner batch 98304、micro-batch 2048、updates 40。

最新状态检查时四 rank 均运行，公共 generation 为 `step-000003981312`。rank0 最近完整轮的
计时为：`iteration_wall_sec=410.47`、`rollout_sec=217.08`、inner `backward_sec=134.32`、
`sync_sec=5.21`、`checkpoint_sec=15.67`；采样内部计时为
`collection_seconds=233.65`、`cpp_backprop_rpc_seconds=154.40`、
`cpp_leaf_model_seconds=32.50`、`cpp_leaf_decode_seconds=24.62`、
`root_policy_seconds=5.37`、`cpp_begin_rpc_seconds=1.43`、`env_step_seconds=3.89`。
不同计时器的起点/聚合口径略有重叠，因此不能把它们机械相加；在 collection 子计时中，
backprop RPC 仍约占 66%，leaf model 约 14%，decode 约 11%。

工作量关系已核对：`n_steps=128` 且 strict `leaf_batch_size=1` 时，每次 collection 有
`128 * 128 = 16384` 个同步推进轮次；最近轮平均约 982,331 个 leaf evaluation，即每轮
约 60 个活跃 leaf。`cpp_backprop_rpc_seconds` 的计时点包住
`call_workers('nosl_is_az_cpp_backprop_and_leaf_batch', ...)`，因此它包括 grouped worker 的
Python wrapper/pipe IPC、每 worker 串行处理最多 4 个独立树、C++ `backprop + nextBatch +
packed`，以及等待最慢 worker，不能解释为纯 native 算术耗时。

20 秒进程树采样进一步显示 collection 阶段主进程约 0.75--1.0 核、worker 合计约 8.0 核，
总计约 8.8 核；容器 cgroup 配额为 25 核（`cpu.max=2500000 100000`），所以不是 CPU 配额打满，
而是每个同步轮次的短任务/IPC/等待造成并行度不足。该窗口 GPU util 约 5%，说明叶推理是零散
burst；learner 阶段 worker 休眠、主进程约 1 核，GPU util 约 43--48%，也未填满设备。
主机可见 208 逻辑 CPU，但实际训练只能使用 cgroup 的 25 CPU。

代码静态检查发现 learner 还有一个可独立优化的常数瓶颈：每个 inner update 的
`98304/2048=48` 个 microbatch，40 updates 约 1920 次前后向；每个 microbatch 在
`rl/algorithms/accumulating_ppo.py:1622` 对约 14 个监控 tensor 执行 `.detach().cpu().numpy()`，
并在 `:1762-1765` 额外同步多个 loss sum。这些同步不改变训练目标，却会阻塞 GPU，并与重复的
CPU→GPU microbatch 张量构造共同解释 learner GPU 只有约一半利用率。

当前优化优先级：

1. 保持 strict paper 语义时，先把 learner 监控聚合留在 GPU、每次 update 只回传一次标量，
   再实测 micro-batch 4096/8192 的显存和轮时；这不改搜索树，仅改变浮点累积顺序，需独立基准。
2. 若保持 `leaf_batch=1`，实现 grouped worker 的专用 native batch RPC，减少每轮每环境的
   Python wrapper/C++ 边界和 pipe 往返；这比继续改模拟器内层循环更可能降低
   `cpp_backprop_rpc_seconds`，需用普通/packed action 与树统计回归保护。
3. `n_envs` 增大并按比例降低 `n_steps`（例如 192×64 或 384×32）可将 16384 个同步轮次
   减半或减至四分之一、同时增大 leaf/GPU batch，但会改变 rollout 分块和随机样本顺序，属于
   单独训练实验，不能标为纯等价性能优化。
4. checkpoint（约 4%）和 ring gradient sync（约 1--2%）目前不是首要瓶颈。

## 单树顺序不变的跨树流式 leaf inference

用户原始意图：“在不修改训练动力学的前提下做一下效率优化，之后应该会继续提升 n_envs”。
本阶段只优化 grouped worker 的 NOSL collection 调度；没有修改搜索公式、simulation 数、环境 transition、
replay、loss、optimizer 或远端训练。验收条件是同一棵树始终只有一个未完成 leaf，请求/backup/NOSL RNG
顺序保持不变；不同树可以异步进入统一 inference queue；普通同步入口和 `leaf_batch_size>1` 保持旧路径。

`GroupedCachedMaskSubprocVecEnv` 新增 search-scoped 流式 RPC：每个 subprocess group 仍串行拥有自己的环境，
但主进程可按任意完成顺序接收空闲 group，并只向已完成 GPU 前推的 group 下发下一轮。`rl/search/native.py`
新增跨树调度器，按完整 worker group 使用 FIFO，达到目标 leaf 数或最老请求等待超时即前推；默认目标 batch 32、
最长等待 0.5 ms。每棵树仍调用 `nextBatch(1)`，没有引入同树 virtual visits。collector 只在 grouped stream
可用且 `leaf_batch_size=1` 时启用；其他训练、dashboard 和 evaluation 保持同步实现。新增 CLI
`--nosl-is-az-inference-batch-size` 与 `--nosl-is-az-inference-max-wait-ms`，旧 checkpoint 分别兼容为 32 和
0.5 ms，后续增加 `n_envs` 时不需要提高同树 leaf 并发。

监控新增 `nosl_is_az/cpp_stream_wait_seconds`、`inference_batch_size_mean` 和
`inference_batch_size_max`。流式路径下 `cpp_backprop_rpc_seconds` 只统计结果下发开销，worker 阻塞等待单独进入
`cpp_stream_wait_seconds`，因此不能把新旧 `cpp_backprop_rpc_seconds` 曲线直接当成同口径加速比。

## 16 倍宽度训练的 producer/consumer 队列压力诊断

用户原始意图：“你查一下当前是 worker 生产端堆积还是消费端更多”。本次只读检查当前
`u40x16-20260916` / W&B `u40x16s16` 的流式 leaf 调度、最新两轮指标和 rank0 资源状态；
没有停止、重启、调参、同步代码或修改远端训练。

代码口径确认：`complete_searches_streaming()` 以完整 worker group 为调度单位，每棵树始终只有一个
未完成 leaf；worker response 进入主进程 `ready` deque。若 ready leaf 少于目标 `128`，最多等待
`0.5 ms` 凑批；若 ready 为空，则在 `receive(None)` 阻塞直到至少一个 worker group 返回。
`cpp_stream_wait_seconds` 同时包含这两类等待，目前没有直接记录 ready queue 长度或高水位。

第二轮完整指标（`global_timesteps=393216`）与首轮稳定一致：推理 batch 平均
`68.55/128`（约 53.6%），最大 `142.75`；`50,192.25` 个 batch 共完成约
`3,440,212.75` 个 leaf。完整 collection 为 `1,012.94 s`，其中 leaf model 计时
`706.55 s`（约 `14.08 ms/batch`），stream wait `172.66 s`（约 `3.44 ms/batch`），
decode `58.88 s`，backprop dispatch `20.61 s`。这些子计时不与其他训练计时机械相加。
由于非空 ready 队列每批最多只允许 `0.5 ms` 凑批，全部 `50,192.25` 个 batch 最多只能产生
约 `25.10 s` 的有限凑批等待；因此至少约 `147.57 s` 是 ready 为空时等待首个 worker 返回。
首轮也得到相同下界：`180.51 - 52,242.75 * 0.5 ms = 154.39 s`。这直接排除了
worker 结果长期堆满 ready queue 的形态。

rank0 在 collection 阶段的 25 秒 `/proc` 差分采样为：trainer `0.952` 核，24 个 worker
合计 `5.834` 核，总计 `6.786` 核；cgroup 配额为 25 核。同期 RTX 5090 设备级 GPU util
平均 `13.04%`（范围 `9%--16%`），显存平均约 `3,055 MiB`。GPU util 是设备级采样，
但该窗口进程仍在 collection，且没有发现其他训练作业。

结论需要分两个维度表述：按“积压位置”看，当前不是 worker 生产结果堆积，而是主进程经常拿不到
足够 leaf，batch 约半满且 ready 队列有明确的空窗；按“墙钟耗时”看，消费端 leaf model 前向仍是
最大单项，约占 collection 的 70%，只是以大量偏小 batch 间歇运行。当前形态是生产到达粒度、
单树 backpressure 与消费端小 batch 服务时间共同造成的流水线不饱和，不能简化为“CPU worker 已打满”
或“GPU 队列已堆满”。后续若优化，需先增加 ready queue depth/empty time 直接监控，再分别验证 producer
并发和 consumer 前向；本次未实施优化。关联 TODO `PERF01`。本节随当前提交。

## 当前训练吞吐的下一步优化顺序

用户原始意图：“那接下来怎么改进训练速度”。本次范围是基于上一节实测与当前实现给出受控优化顺序；
没有修改训练、搜索配置或远端进程。

当前不应继续只放大 `n_envs`：384 个 env 仍被绑定为 24 个原子 worker group，每组 16 个 env 在
`_group_worker()` 内串行执行，整组完成后才返回；增加 env 而不增加 group 数只会扩大组内 head-of-line
blocking。最低风险的配置 A/B 是保持 384 env、128 simulations 和所有训练参数不变，分别测试
`envs_per_worker=16/8/4`（24/48/96 worker），优先看 48 worker 是否能在 25 核配额内把平均 inference
batch 提高到接近目标。当前 worker 仅使用约 5.8 核，存在增加独立 group 的资源余量，但 96 worker
可能开始受到上下文切换、RSS 和 IPC 影响，不能未经实测直接作为生产值。

同一 A/B 应先测试 `inference_max_wait_ms=0.5/1/2/4`，目标 batch 保持 128。该等待只跨独立树凑
GPU batch，不增加单树 outstanding leaf，因此不改变 strict-paper 的单树搜索规则。当前模型调用约
`14.08 ms/batch`，额外等待 1--3 ms 若能显著提高约 68.55 的平均 batch，可能以更少前向调用换取
净收益；若 batch 不增则立即回退。不能直接把等待调大并用训练曲线猜测吞吐。

用户随后追问“gpu 前向批次扩大如何”。当前不应直接把 `nosl_is_az_inference_batch_size` 从 128
改到 256：实际平均 batch 只有 68.55，说明供给连 128 都未填满；相同 0.5 ms 窗口下，提高目标不会
凭空产生 leaf，通常仍会以相近的小 batch 前向。应先通过 48 worker、较小 group 或 1--4 ms 凑批让
实际 batch 的 p50/p90 接近 128，再用真实 observation 对 `64/96/128/192/256/384` 做稳定 graph 的
samples/s 曲线，选择吞吐拐点。若 128 已稳定填满，再测试 target 192/256；若仍只有约 70，则继续增大
目标无效。这里扩大的是独立树之间的 GPU inference batch，`leaf_batch_size` 必须保持 1；后者会增加
同一树的并行 leaf/virtual visit，改变 strict-paper 搜索语义。训练反向的 `micro_batch_size=8192` 是
另一参数，不能与 leaf inference batch 混用。

消费端优先补充两类监控：ready leaf 的时间加权均值/最大值、空队列时间、under-target flush 数，
以及 CUDA graph hit/capture/eviction、H2D、graph replay、D2H 的独立 CUDA-event 计时。静态检查发现
`CombatLeafGraphs` 的 cache key 包含精确 batch shape 和 active relic width，容量仅 32；动态 batch
可能造成 graph 反复淘汰和 capture，而当前 `cpp_leaf_model_seconds` 把这些开销与真正模型计算合并。
这是高风险候选但尚未由运行指标证实。若确认 churn，使用少量固定 batch bucket（候选
`64/96/128/144`，padding 后丢弃虚样本输出）并固定或分桶 relic width；同时把 logits/value 合并到
预分配 pinned host 输出、一次异步 D2H 和一次同步，避免每批两次 `.cpu().numpy()` 分配/同步。

结构性优化是在保持每棵树一次只有一个 pending leaf 的前提下，取消“16 个 env 全部完成才返回”的
group 原子屏障：worker 按 ready env 发出 packed partial response，主进程统一入队，完成推理后只唤醒
对应树；长期可用共享内存 ring 和双缓冲让下一批 decode/H2D 与当前 GPU replay/D2H 重叠。这保留单树
visit/NOSL 顺序，但改变跨树调度和浮点 batch shape，需要固定 seed 的 root action/visit 回归和生产长度
collection 验证，不能宣称跨设备 bitwise。

推荐执行顺序：先加入监控；再从同一 checkpoint、同一 seed 做不更新模型的固定 leaf 工作量 A/B，
依次测试等待窗口与 48 worker；随后依据 graph churn 指标实现固定桶和输出 buffer；最后才做 partial
worker response/共享内存。验收以 leaves/s、collection wall time、batch 分布、ready-empty 时间、CPU、
RSS、GPU util/VRAM 和固定搜索结果共同判断。当前 learner 约 `102.76 s`、collection 约 `1012.94 s`，
所以先优化 collection；replay 填满后再评估把 micro-batch 从 8192 提到 16384/32768，以及移除
per-microbatch CPU 同步。降低 simulations 或增加单树 `leaf_batch_size` 会改变训练/搜索动力学，不列入
本轮等价优化。关联 TODO `PERF01`。本节随当前提交。
