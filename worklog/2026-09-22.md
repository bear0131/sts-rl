### Dynamic NOSL update-count decision boundary

User intention: determine whether the live `nosl_is_az_updates=40` should be
raised or lowered during training, and how to change it without confusing
learner throughput with collection throughput. Scope here is read-only live
diagnosis and a schedule design; the production run was not stopped or
reconfigured.

The current implementation treats `nosl_is_az_updates` as the number of
independent replay samples, synchronized gradient reductions, and Adam steps
after each collection. It is not the four-microbatch gradient accumulation
inside one update. At the live geometry (`batch=98304`, replay capacity
`524288`, `max_old_fraction=0.90`) each update reserves about `9831` current
collection rows. The latest 60 rank0 records had mean fresh roots `12611`, so
the expected average exposure of a fresh root is approximately:

| updates | fresh-root exposures | sampled rows/rank/collection |
|---:|---:|---:|
| 10 | 7.8 | 983040 |
| 20 | 15.6 | 1966080 |
| 40 | 31.2 | 3932160 |

This follows `exposure ~= updates * batch * (1-max_old_fraction) /
fresh_roots`; the replay sampler's without-replacement branch does not change
that expected total. Therefore changing the count changes train-to-data ratio,
Adam bias-correction step count, and policy dynamics. It cannot be described as
a semantics-preserving speed knob.

Read-only live logs at the current run (`u40x4-ruleupper-v1-transformer-
reduced-768x16-20260922`) show, over the latest 60 complete rank0 records,
mean iteration wall `168.916 s`, mean rollout `72.119 s`, mean NOSL backward
`65.063 s`, and mean fresh roots `12611.467`; the corresponding mean global
throughput is about `291` env steps/s. Policy loss, target KL, and top-1
agreement are nearly flat (`0.934`, `0.414`, `0.643`), while floor mean is
noisy around `29.74`. A linear learner-time estimate therefore predicts about
`136 s`/round for `U=20` and `120 s`/round for `U=10` at the same rollout,
before policy-dependent collection changes. No evidence supports increasing
above 40.

Historical paired four-rank tests do not establish a universal quality winner:
`U=40` retained one favorable HP endpoint but cost about 12% more wall time
than the `U=5` baseline, while equal sampled-row `U=10`/`U=20` branches had
mixed terminal and replay-corpus results. Thus the conservative production
candidate is `U=20` for a throughput/quality test, with `U=10` reserved for a
speed-first phase; do not infer quality from in-sample policy loss alone.

Recommended controller (not deployed): choose only at a completed collection
boundary, compute a smoothed global fresh-root count, and target a fixed fresh
exposure `E` rather than a fixed wall time:

```text
quota = ceil(batch_size * (1 - max_old_fraction))
U_next = clamp(round(E * EMA(fresh_roots) / quota), U_min, U_max)
```

Use `E=16` as the first balanced probe (`U` usually near 20), bounds 10--40,
an 8--12 collection cooldown, and a maximum change of 10 per decision. Rank0
must compute and broadcast the integer to every rank. A held-out replay metric
(target KL/MAE and fixed-seed game evaluation) should gate increases; a falling
throughput or an in-sample loss improvement alone must not. The controller's
planned/applied count, fresh roots, quota, exposure, and state must be saved in
the recovery bundle.

The current trainer has no in-process update schedule or persisted controller
state. Today the safe mechanism is a coordinated stop at a complete recovery
generation followed by resume with a new args file; changing the args file
while the process is running has no effect. A true dynamic controller remains a
separate implementation/validation task. Production remains on `U=40` while
this decision is pending.

### Model-size and update-dynamics diagnosis

User intention: determine whether the reduced model's worse curve can be
partly caused by model-size-dependent update dynamics rather than capacity
alone. No remote process, STOP marker, replay, optimizer state, or production
configuration was changed.

The curve alignment is consistent with an early, persistent fit gap. At about
0.49M / 1.97M / 3.93M / 7.86M global steps, reduced-vs-large floor means were
approximately 16.28 vs 16.68, 18.34 vs 25.50, 23.23 vs 28.94, and 26.43 vs
31.96. At 7.86M the reduced model had policy target KL about .437 versus .401,
top-1 agreement .626 versus .658, policy loss .969 versus .914, and value MAE
.0395 versus .0349. Thus the difference appears before late-capacity collapse,
but these runs are not a causal same-replay comparison.

The main confound is accumulation geometry. The large fresh/occupancy run used
`micro_batch=2048` (48 microbatches per 98,304-row learner update), while the
reduced runs used `micro_batch=12,288` or `24,576` (8 or 4 calls). Effective
batch, U=40, replay old-fraction, LR, and search settings were otherwise held
close. BF16 accumulation order, reduction kernels, and clip-boundary timing can
therefore change the optimizer input even when the mathematical batch is equal.

Read-only local diagnostics are in
`runs/local/model-size-20260922/same-observation-probe-v4.json` and the earlier
`same-observation-probe-v2.json`/`v3.json`. On the same 16 saved observations
and legal-action masks, comparing current large (`d_model=256`, step 7.72M)
and reduced (`d_model=100`, step 8.11M) checkpoints produced:

* policy entropy: approximately `.733` vs `4.082`; valid-logit standard
  deviation: `2.55` vs `.748`;
* with the same uniform policy target and policy loss only, pre-clip gradient
  norm: `125.4` vs `22.3`, clip scales `.00399` vs `.0224`;
* using each checkpoint's existing Adam moments, predicted one-step relative
  parameter change: `1.94e-4` vs `7.77e-5` (about 2.5x).

Including the value loss increases the gap in this probe, but the policy-only
result shows it is not solely a value-head scale artifact. A separate early
checkpoint probe showed a much larger output-calibration difference, but it is
not used as a production claim because it is an initialization/state diagnostic
rather than a fixed-replay learner experiment.

Interpretation: there is credible evidence for a model-size-dependent update
regime (logit temperature, gradient scale, global clipping, and Adam effective
step), in addition to the reduced model's lower representation capacity. The
current evidence does not establish which factor dominates online learning.
The decisive experiment remains a 2x2 fixed-replay clone: both widths at
`micro_batch=2048` and `24,576`, with identical labels, then LR scales and
`U` held fixed while recording clip scale, target KL, top-1 agreement, value
MAE, gradient norm, and parameter delta. No complete local `learner.pt` replay
bundle was available to run that test in this stage.

Operational recommendation: do not dynamically change production `U=40` or LR
based on these diagnostics alone. If a reduced-model branch is tested later,
first equalize microbatch geometry and use a short isolated continuation; test
LR around `1.5x` only as an explicit hypothesis, with held-out/fixed-seed
evaluation gating promotion. Keep the current 768x16 production run running.
